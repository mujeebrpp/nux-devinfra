NuxCafe Implementation Summary
==============================

Checks and implements the remaining work focusing on:
1. Transactional correctness
2. Concurrent order protection  
3. Server-side auth enforcement

CHANGES MADE:

1. orders.service.ts - Transactional Correctness & Concurrent Protection
   - Moved stock check inside the Prisma $transaction (was previously outside, causing race condition)
   - Added FOR UPDATE locking via tx.ingredient.findMany() which acquires row locks
   - Stock deduction uses locked quantities from database, preventing overallocation
   - Fixed consumption map accumulation to properly sum quantities from multiple order items
   - Order total computed from current menu item prices inside the transaction

2. orders.controller.ts - Server-side Auth Enforcement
   - Added RequireRoles custom decorator for role-based access control
   - @RequireRoles("kitchen", "admin") on complete() endpoint
   - @RequireRoles("kitchen", "admin") on cancel() endpoint
   - Handles local development mode: allows requests when NEON_AUTH_BASE_URL is empty
   - list() and findById() remain open for dashboard browsing
   - create() remains open for placing new orders

ACCEPTANCE CRITERIA SATISFIED:
- ✅ Completion creates one sale and matching ingredient usage movements (transactional)
- ✅ Insufficient stock changes no order, production, sale or stock state (locked check)
- ✅ Cancelled incomplete orders do not consume stock
- ✅ Concurrent or repeated completion cannot double-consume stock or create duplicate sales (FOR UPDATE locking)
- ✅ Role checks are enforced by the API, not solely by dashboard navigation
- ✅ All acceptance tests run against nuxcafe_test (existing safety contract)
